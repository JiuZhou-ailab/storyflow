# CONTEXT

Glossary of terms for the Storyflow performance-optimization effort. Definitions only — no implementation details.

## Performance

- **Performance scope** — In this project, "performance" means three axes only: *interaction responsiveness* (typing latency, list scrolling, panel switching), *startup time* (cold start to first usable frame), and *memory footprint* (growth over long-running sessions, pressure from large sessions). Backend/worker throughput is explicitly out of scope.
- **Perf baseline** — A re-runnable measurement script plus its recorded result, captured *before* an optimization lands. Every optimization must leave one behind; it doubles as the regression guard.
- **Symptom scenario** — A concrete, user-observable slowness (e.g. "opening session X takes 3 s"). Symptom scenarios drive prioritization; perf baselines drive acceptance.
- **Axis priority** — The fixed ordering of the three performance axes: interaction responsiveness > memory footprint > startup time. Rationale: Storyflow is a long-running workbench — interaction cost is paid hundreds of times a day, memory decay degrades into interaction cost, startup is paid once.
- **Standard fixture** — The synthetic dataset all perf baselines run against: real-data distribution shape (message length, tool-call density sampled from actual session jsonl) scaled up to target size — 20 workspaces, 300 sessions per workspace, long sessions of 1000 messages (~30% tool-call lines), writing documents of 400 chapters. Targets are product-scale, not current-usage-scale.
- **Interaction budget tiers** — The three acceptance thresholds for the interaction axis, all P95 at standard-fixture scale: *continuous* operations (typing echo, scrolling, streaming deltas) < 16.7 ms per render+commit; *discrete* operations (session switch, panel open, search results) < 100 ms; *heavy* operations (opening a 400-chapter document, global search) < 1 s and must show loading feedback.
- **Memory targets** — Two orthogonal sub-metrics at standard-fixture scale: *steady-state* renderer heap < 500 MB with the fixture fully loaded; *leak check* — after a fixed interaction loop (100 session switches, document open/close cycles) and a forced GC, heap returns to within +10% of the pre-loop baseline. Leak is judged by relative growth, never absolute size.
- **Startup target** — Cold launch to first editable writing document < 3 s on the reference Apple-silicon Mac. Diagnostic sub-budgets are launch to interactive Project Hub < 2 s and project click to editable document < 1 s; session/LLM hydration is not part of project readiness.
- **Structural optimization** — An optimization that changes the data layer (storage format, indexing, message pagination, IPC protocol) rather than the render/load layer (memoization, virtualization, lazy mounting, subscription narrowing). Structural optimizations are allowed but each one requires its own ADR before implementation; render/load-layer optimizations do not.
- **Done state** — The performance effort ends when all quantified targets pass at standard-fixture scale (interaction budget tiers, memory targets, startup target). After that, perf work is maintenance only: CI proxy-metric guards plus a local e2e run before releases. If a target proves far harder than expected, the move is to reopen its ADR and renegotiate the target — never to silently extend the effort.
